# 消除低清→高清封面的几何跳变

2026-09-24

## 问题

封面模式下，切歌瞬间先显示 MediaSession 那张 363 方图，高清图异步到位后替换。
由于高清图请求的是 **4:5**，而低清那张是**方形**，两张图的宽高比不同——
`AlbumBackdrop` 按「图自身宽高比」排版，于是替换的那一刻整块封面发生
**可见的 zoom / 位移**，而不只是变清晰。

预取下一首的封面可以规避这个问题（提前拉好，切歌时直接上高清），
但**实测证明拿不到下一首**，见下节。

## 调研一：能否提前知道下一首 —— 不能

真机取证（网易云 / One UI 5.1 / SM-G9810）。

### 网易云确实发布了队列，但那个队列与播放内容无关

`dumpsys media_session` 显示 `queueSize=447`，队列项也确实带着我们要的东西：

```
q[0] qid=0 mediaId=other_id__28643004 title=Miss You Tonight
     iconUri=http://p2.music.126.net/QT4SOgK4Qsgos7vmmB0faQ==/16659800184735270.jpg
             ?imageView=1&thumbnail=256z256&type=webp&quality=80
```

`mediaId` 去掉 `other_id__` 前缀就是真实歌曲 id，`iconUri` 更是直接给了 `picUrl`
（只带了个 256 缩略参数）。**如果**能定位当前位置，预取连 `song/detail` 那次
往返都能省掉。

但定位不了：

1. **`activeQueueItemId = -1`** —— 会话从不告诉我们播到第几条。
2. **当前播放的歌根本不在队列里**。连续切四首，每首都按 id 在 447 条里找：

   ```
   curIndexInQueue=-1  (cur=108473)
   curIndexInQueue=-1  (cur=254072)
   curIndexInQueue=-1  (cur=3347910671)
   curIndexInQueue=-1  (cur=255204)
   ```

   四首全部找不到。同时队列头始终是 `Miss You Tonight / Honey Honey / 浴室`
   （index 0/1/2），`queueSize=447` 24 次采样一次没变——播放走了四首歌，
   队列纹丝不动。那 447 条是某个**静态歌单快照**（extras 里的
   `from_player_list` 是旁证），不是当前播放队列。

3. **声明的能力里没有队列导航**。`actions=822` 解出来是
   `PAUSE|PLAY|SKIP_TO_PREVIOUS|SKIP_TO_NEXT|SEEK_TO|PLAY_PAUSE`，
   **不含 `SKIP_TO_QUEUE_ITEM`**——网易云自己就把这个队列标成了不可导航的，
   与 `activeItemId=-1` 一致。它发布队列是给 Android Auto / HiCar 列个歌单看
   （session extras 里有 `hicar.media.bundle.FOR_HICAR`），不是给人当游标用。

4. **session extras / metadata 里也没有 next 字段**：

   ```
   sessionExtras = hicar.media.bundle.UI_STYLE, hicar.media.bundle.FOR_HICAR
   metadataKeys  = ALBUM_ART, ARTIST, DISPLAY_ICON, DISPLAY_SUBTITLE, DURATION,
                   USER_RATING, ART, DISPLAY_TITLE, MEDIA_ID, ALBUM, TITLE
   ```

### 剩下两条路都是「猜」，不做

- **自己查网易云歌单接口算下一首**：绕不开随机播放、心动模式、私人漫游这些
  「下一首由服务端现生成」的模式，而网易云不暴露播放模式（custom action 里
  有个「播放模式」按钮，但只能按、读不到当前值）。
- **读网易云私有缓存/数据库**：依赖 root 与内部结构，改版即静默失效。
  CLAUDE.md 对「读私有缓存拿原图」已经否掉过同一类做法。

**所以预取这条路封死**。本设计不依赖预取，改为让跳变在结构上不可能发生。

## 调研二：网易云的 `?param` 就是纯居中裁切 —— 我们可以自己裁

18 首歌，每首拉 `?param=800y800`（方）与 `?param=640y800`（正好 4:5），
逐像素比对两个假设：

- **crop**：4:5 图 == 方图正中间那 640 列
- **squeeze**：4:5 图 == 方图整体压扁

```
id                   orig     crop  squeeze
1360464825   (1425, 1425)    0.000   42.111   ← 逐字节相同
167827       (3000, 3000)    0.000   48.220   ← 逐字节相同
186016       (1080, 1080)    0.000   68.518   ← 逐字节相同
2689044614     (800, 800)    0.000   16.992   ← 逐字节相同
33894312     (1920, 1920)    0.000   60.403   ← 逐字节相同
108473       (3000, 3000)    0.000   86.530   ← 逐字节相同
254072       (1500, 1500)    0.000   50.496   ← 逐字节相同
255204       (2048, 2048)    0.000   65.377   ← 逐字节相同
1974443814   (6000, 6000)    0.075   40.227
3347910671   (1280, 1280)    0.045   51.138
411214279    (2480, 2480)    0.062   49.697
65528        (1024, 1024)    0.046   32.773
567145047      (800, 800)    0.035   60.837
483378334    (4429, 4429)    0.029   27.339
2128117547   (2000, 2000)    4.848   67.607
```

**八首 RMSE 恰好 0.000**——不是「接近」，是逐字节相同。其余多在 0.03~0.08，
比 JPEG 重编码噪声还小一个数量级（实测同图重新编码一次 RMSE 就有 0.8~1.7）。
唯一偏大的 2128117547 是 4.85，仍远低于 squeeze 假设的 67.6，且从原图直接裁
算出来是 4.56——差别只是多走了一次重采样。

**结论：网易云没有做任何针对竖图的构图优化、art direction 或智能裁切。
我们自己从方图裁，得到的与找它要 4:5 是同一张图。**

### 三个附带发现，都影响设计

1. **原图不一定是方的**。`28643004` 的原图是 **852×1136**（3:4 竖）。
   现有代码与注释里「网易云的原图恒为方形」这个假设是错的
   （`paramFor` 的单值 `sourceEdge` 参数、`ArtworkCache` 的注释都建立在它上面）。
   该首的方图与 4:5 图是**各自从原图独立居中裁**出来的（按此假设复算
   RMSE 6.2 / 7.4，同量级噪声）。

2. **静默回落方图的触发点比想象中低**。`297788` 原图 553×553，请求 `640y800`
   直接拿回 553×553 方图；`4874308` 原图才 348。而请求 `440y550`（长边 550 < 553）
   就正常返回 440×550。**小原图相当常见，不是边缘情况。**

3. 第 2 条正是「低清切成 4:5、高清回来却是方图」这个担忧的真实来源——
   它确实会发生。本设计通过「只请求方图」把它彻底消除。

## 设计

### 核心不变式

把「比例」从网络层搬到渲染层：网络层只负责拿**尽可能清晰的方图**，
渲染层负责把任意来源的图裁进**同一个 4:5 框**。

```
363 方图  ──┐
            ├──► 同一套裁切（居中裁进目标比例框）──► 同一个排版矩形
高清方图  ──┘
```

**低清与高清必须产生逐像素对应的排版。** 只要两条路进的都是方图、
出的都是同一个框，几何就恒等，切换时只有清晰度变化。这与「多档模糊之所以
看不出边界」是同一条道理：像素一一对应。

这条不变式的前提由调研二保证。它使跳变**在结构上不可能发生**，
而不是「大概率不发生」。

### 网络层：只请求方图

- 请求参数恒为 `?param=${edge}y${edge}`，`edge = min(屏幕宽, 源图短边)`。
- **方图永远不会触发静默回落**：超限也只是拿到原图本身，比例不变。
- `paramFor` 的等比降级逻辑退役，退化成一次 `min`。它现在要处理
  「长边超限 → 等比降级 → 保住比例」，是 CLAUDE.md 明说的
  「整条链路里最容易算错的一环」；方图不需要保比例。
- `probeSourceEdge` **保留但降级**：仍要探原图尺寸，但作用从「保住比例」
  变成「别请求超过原图、白浪费」。算错不再有视觉后果。
- 修正「原图恒为方」的错误假设：改成按**短边**限幅（求方图时短边才是约束）。
  `ArtworkFetcher.Result.sourceEdge` 相应改为携带短边。

#### `aspect` 要从网络层彻底移除

`ArtworkFetcher.fetch(songId, aspect, targetWidth)` 的 `aspect` 参数删掉，
`ArtworkCache.Key` 里的 `aspect` 字段也删掉（键退化成 `mediaId` + 请求边长）。

这不只是清理：比例已经不影响拉回来的字节了，若还留在缓存键里，
**实验室里每换一档比例都会白白重拉一次网络**（键变了 → 未命中 → 重新
请求同一张方图）。而换比例现在本该是纯渲染侧的事，应当**立即生效、零网络**。

同理 `MainActivity` 拉封面那个 `LaunchedEffect` 的 key 里要去掉 `coverAspect`,
否则换比例仍会重跑一次拉取。

### 渲染层：自己裁

`AlbumBackdrop` 目前按「图自身宽高比」排版：

```kotlin
// 现在：低清方图得 1.0，高清 4:5 图得 1.25，几何不同
val imageAspect = bitmap.height.toFloat() / bitmap.width.toFloat()

// 改后：恒为目标比例，与图本身是方是竖无关
val targetAspect = aspect.hRatio.toFloat() / aspect.wRatio
```

配套地，`BlurLayer` 的 `contentScale` 从 `FillBounds` 改为 **`Crop`**：
框的形状由目标比例定死，图用 Crop 居中填进去——**这就是我们自己做的那次
居中裁**，与网易云做的那次等价。

这推翻了现有注释「用 FillBounds 而非 Crop：真出现非方封面时宁可轻微拉伸，
也好过把两侧裁掉」。那条的前提是「封面恒为方形」（已证伪），且现在
**框不再等于图的形状**，FillBounds 会把方图压成 4:5，那才是真变形。
要一并更新注释说明翻案理由。

兜底层（`fillScreen = true`）不受影响，它本来就是 Crop 拉满。

`AlbumBackdrop` 需要新增一个 `aspect: CoverAspect` 参数——它现在得知道
要裁成什么形状，而不是从 bitmap 推断。

### Crossfade

即便几何恒定，从 363 上采样到清晰高清仍是一次可见的「变清晰」。
在 `AlbumBackdrop` 内部，当传入的 bitmap 变化且**是同一首歌的升级**时，
叠画旧图与新图，新图 alpha 从 0 走到 1，**250ms**。

约束：

- **只在「同一首歌、低清→高清」时淡入**。切歌是换歌，该直接换——
  切歌时旧图淡出反而像卡顿。判定信号从调用方传下来：`TrackpadScreen`
  目前传 `track?.hiResArtwork ?: track?.artwork`，需把 `mediaId` 一并传下去当 key。
- **不对 blur 半径做动画**，沿用现有口径（半径每变一次要重新生成全屏模糊，
  会和歌词逐行动画抢帧预算）。crossfade 只动 alpha。
- 旧图要多持有淡出那段时间的强引用，与 `ArtworkCache`「不主动 recycle」
  同一口径——正在淡出的那张若被回收会抛 `trying to use a recycled bitmap`。

250ms 是待验证的初值，真机看过效果再定。

### `CoverAspect` 保留，语义改变

保留枚举，但语义从「请求比例」变成「**渲染裁切比例**」。理由：
实验室「逐档试比例」的能力仍然有用，而且现在**所有档位都必然生效**
（自己裁不会被接口吞掉），反而比以前更可信。

默认仍是 **4:5**。已知代价不变：切掉原图横向 20%，含封面上贴边的标题字
（这是先前用户拍板接受的取舍）。

### 实验室：多放几个比例，供肉眼验证

在 `CoverAspect` 里**补充更多档位**供真机逐档试。现有五档
（1:1 / 4:5 / 2:3 / 9:16 / 3:2）基础上加入中间档，让 1:1→4:5 之间
有更细的粒度，例如 **5:6**、**3:4**、**5:7**。

实验室界面随之改动：

- 不再有「这档会被回落成方图」的情形，**标灰的口径只剩「铺不满屏幕宽度」**。
- `AspectRow` 标注的尺寸改为「渲染裁切后的框尺寸」而非「请求尺寸」——
  请求恒为方图，标请求尺寸就失去区分度了（所有档一样）。
- `SourceInfo` 里的「高清封面：W×H」现在恒为方形，仍然有用（它报的是
  实际拿到的清晰度），但措辞要改，别让人以为那是最终显示的形状。
- 换档**不再触发重拉**（见上节），所以 `LaunchedEffect` 的 key 里去掉 `aspect`；
  换档应当立即重绘。「清缓存重拉」按钮保留，它针对的是「接口这次返回异常」。
- 页面说明文案要重写：现在的说明讲的是「接口居中裁切 + 静默回落」，
  而这两件事都已不在链路里。

### 测试

- `CoverAspectTest` 改写：删掉「降级后比例保持」的五档 × 五源图矩阵
  （不再有非方请求），换成「请求边长不超过源图短边」「源图极小时不为 0」。
- **新增核心不变式的断言**：给定低清尺寸（363×363）与高清尺寸
  （如 1080×1080、852×1136）以及同一个目标比例，算出的排版高度必须相同。
  这正是「代码里看不出来」的那类约束——把它抽成纯函数以便 JVM 单测。
- 真机回归项（补进 CLAUDE.md）：切歌时封面**几何不变**、只有清晰度变化。
  逐帧量的话，低清→高清那一刻封面上下沿的位置不应移动。

## 不做

- **预取下一首封面**：调研证明拿不到下一首（见调研一）。
- **按歌名/文本搜索匹配封面**：沿用现有口径，文本匹配是猜的。
- **读网易云私有缓存**：依赖 root 与内部结构，改版即静默失效。
- **把比例做成用户可见的设置项**：它仍是开发期取景器，只存内存不落盘，
  理由同另两个实验室。
