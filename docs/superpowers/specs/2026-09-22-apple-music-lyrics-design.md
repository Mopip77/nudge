# 歌词 UI 对齐 Apple Music

## 现状与问题

当前实现（`ui/LyricsOverlay.kt`）与 Apple Music 的差距集中在四点：

1. **字号有别**：当前行 26sp、其余行 22sp，靠 scale 放大表达。Apple Music 的
   非逐字模式里高亮行与其余行**字号一致**。
2. **模糊区分度过大**：`2.6dp/行` 封顶 `12dp`，第 5 行开外彻底化开成色块。
   Apple Music 是在整个可视区间内**缓步加深**——下一行就已有可见模糊，
   但即使最远处仍能认出字。
3. **换行是整体平移**：整列共用一个 `offsetY`，所有行同时、同速变化。
   Apple Music 是下一行先顶上来，后续行以**递减的相位**被拖上来。
4. **入场无阻尼**：从裁切边界外进来的行线性到位，缺少「被链条拽进来」的过冲感。

## 决策

| 维度 | 选择 |
|------|------|
| 高亮方式 | 纯透明度 + 零模糊，不再有字号/scale 差异 |
| 模糊曲线 | 上下对称，第 1 行起步，缓升到最远约 5–6dp |
| 错峰强度 | 中等，相位差体现为每行约 25–40ms 的到位延迟，拖尾 3–5 行 |
| 阻尼范围 | 整条链都用弹簧，越往下阻尼越弱（刚度随距离递减） |
| 验证 | 真机装包实测 |

## 架构

### 放弃「整列单一位移」模型

错峰要求每行有各自的相位，一个 `translationY` 表达不了。改为**每行持有自己的
`Animatable`**，目标值是该行应在的绝对位置与其在 Column 内排版位置之差。

被否掉的两个替代：

- **整列平移 + 每行叠加衰减滞后偏移**：两套动画叠加，过冲会与主位移互相干扰，
  调参时分不清是哪一层的问题。
- **LazyColumn + animateScrollBy**：滚动是单一曲线，做不出逐行相位差，
  且会重新引入触摸语义——歌词层是刻意只读的。

### 错峰与阻尼是同一套机制

弹簧刚度随距离递减时，同时产生两个效果：靠近当前行的行更快到位（相位差 → 错峰），
越远的行阻尼比越低（过冲更明显 → 入场阻尼）。因此不引入独立的 delay 参数，
只用一组随 `distance` 插值的 spring 参数表达，可调面收敛成两个端点值。

### 保留不变的部分

- 纯展示、不接触摸（盲操下可交互歌词与手势语义冲突）
- `rowHeights` 按实测高度累加（折行歌词的位置基准）
- 窗口化渲染、上下边缘 DstIn 淡出
- API < 31 自动降级为只靠 alpha 分层

## 风险

- **每行一个 Animatable**：窗口约 20 行，动的是绘制阶段的 `translationY`，
  不触发重组或重测量。仍需真机确认不影响手势响应——这块区域同时是触摸板。
- **过冲与边缘淡出的相互作用**：回弹可能让行短暂越过裁切边界。淡出区占 12%，
  预期能吸收，需实测确认。

## 验证

真机装包实测，重点：

- 换行时逐行相位差可见，不是整体平移
- 最远处行仍能辨认文字
- 连续快速换行（快歌）时不出现累积错位
- 手势响应无可感知延迟
