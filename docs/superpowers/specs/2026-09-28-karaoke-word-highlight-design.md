# 歌词逐字高亮（扫光）设计

日期：2026-09-28

把当前行的整行高亮，升级成随演唱从左往右扫过的逐字高亮（Apple Music 式）。
数据来自网易云的 `yrc` 字段。

## 一、接口取证

以下全部是本次实测结论，不是推断。

### `yrc` 就是逐字歌词，但要换请求参数

现有请求 `lv=1&kv=1&tv=-1` 只返回行级 LRC。逐字数据在 **`yrc`** 字段，
要加 **`yv=1&yrv=-1`**（译文的逐字配套版是 `ytlrc`，由 `ytv=-1` 带出）。

加参数是**纯增量**：实测 `lrc` / `tlyric` 两个字段不受影响，行级路径零风险。

格式：

```
[11460,2730](11460,210,0)I (11670,180,0)do (11850,120,0)the (11970,540,0)same ...
 行起  行长   字起  字长 ?
```

全是**绝对毫秒**。校验过的结构不变式（51 行样本，零违例）：

- 字级起点单调递增
- 末字终点 == 行起 + 行长（误差 0）
- 括号里第三个数字**恒为 0**，用途不明，直接丢弃
- 行首有 `[0,0](0,0,0) 作词 : XXX` 这类元信息行，要像 `LrcParser`
  丢弃无时间戳行一样丢掉

### 覆盖率约 40%，所以逐字只能是增强档

抽 12 首实测，5 首有 `yrc`、7 首没有（含热门老歌与纯音乐）。
**行级高亮必须完整保留做降级，不能替换。**

### 关键：`yrc` 与 `lrc` 不在同一条时间轴上

这是本次最重要、也最容易写错的一条。

按时间戳精确匹配的命中率近乎为零（5 首样本，命中 1~8 行 / 约 50 行）。
按文本匹配后量偏差：

| 歌曲 | 中位偏差 | 单曲内范围 |
|---|---|---|
| 1859245776 | −243ms | [−523, +2000] |
| 1901371647 | −50ms | [−14490, +4629] |
| 1974443815 | −2ms | [−130, +360] |
| 33894312 | −80ms | [−200, +240] |
| 4877111 | −240ms | [−340, 0] |

**偏移非常数**，单曲内范围可达半秒以上，无法靠一个补偿量修正。

### 但接口自带两套**自洽**的配对

| 配对 | `ytlrc` 命中 `yrc` | `tlyric` 命中 `yrc` |
|---|---|---|
| 1859245776 | **35/35** | **0/35** |

`ytlrc` 与 `yrc` 精确同轴，`tlyric` 与之完全不沾边。
即接口给的是 `(lrc, tlyric)` 与 `(yrc, ytlrc)` 两套各自自洽的数据，
**跨轴混用必然错位**。

## 二、架构决策：整对替换，绝不跨轴合并

`LyricsRepository` 拿到响应后二选一，**以整首歌为粒度**：

- `yrc` 非空 → 用 `(yrc, ytlrc)`，得到带字级时间表的行
- 否则 → 走现有 `(lrc, tlyric)`，行为与今天**逐字节相同**

降级发生在整首歌粒度，不会出现同一首歌里有的行准、有的行偏。

**为什么不把 yrc 的字级时间表挂到现有 lrc 行上**：那正是 `LrcParser`
注释里已经警告过的那类缺陷——「按下标对齐会从第一个缺口起整体错位……
而这在界面上看着像是翻译得不太准，不会被认成缺陷」。这里更糟：
扫光偏半秒是**看得见**的，光会跑在字的前面或后面。

已知代价：有 `yrc` 的歌，译文改从 `ytlrc` 取，可能与 `tlyric` 的措辞、
行数不同。已与用户确认接受。译文缺失在本项目里本就是常态路径。

## 三、数据模型

`LyricLine` 加一个可空字段，口径与 `translation` 一致（null 是常态非异常）：

```kotlin
data class LyricLine(
    val timeMs: Long,
    val text: String,
    val translation: String? = null,
    /** 字级时间表，null 表示这首歌没有 yrc。 */
    val words: List<LyricWord>? = null,
)

/** [startMs] 绝对毫秒，与 [LyricLine.timeMs] 同一时间轴。 */
data class LyricWord(val startMs: Long, val durationMs: Long, val text: String)
```

新增 `YrcParser`，与 `LrcParser` 并列。**纯 Kotlin 无 Android 依赖**，
可 JVM 单测——理由同 `LrcParser`：真实数据的边界情况多，靠真机手测不现实。

`words` 为 null 时渲染侧退化为整行高亮，与今天一致。

## 四、渲染：一个遮罩，不拆字

**不把每个字拆成独立 composable**——一行几十个 `Text` 会让折行逻辑
要自己重写，且行高不再由 Compose 自然决定。

做法是在当前行的原文 `Text` 上挂一层扫光遮罩，用 `drawWithContent`
配 `BlendMode.SrcIn` 把「已唱」与「未唱」两档颜色分开。

### 折行必须精确处理（已决定做精确版）

单个 `Text` 折成两行后，一个朴素的横向渐变会**同时切两个折行**：
唱到一半时上行右半暗、下行右半也暗。那不是「不够精细」，
而是看着像渲染 bug。

折行在这里是**常态不是边缘情况**：`maxLines = 3`、`FONT_SIZE = 27.sp`
偏大，实验室的假歌词里本就专门放了必然折行的样本（CLAUDE.md：
「折行是动画里最容易露馅的场景」）。

精确版做法：接 `onTextLayout` 拿 `TextLayoutResult`，对每个 `LyricWord`
算出它对应的字符区间，查 `getLineForOffset` 与 `getHorizontalPosition`
得到 (折行号, x)。**这是每行一次的一次性计算，不在每帧路径上**
（一行几十次查表，而 `TextLayoutResult` 内部是算好的数组，几乎是纯读）。

每帧只做：按进度找到当前字 → 读它预先算好的 (折行号, x) →
画 **1~3 个** `drawRect`（已唱满的折行画满宽、正在唱的画到 x、
未开始的不画）。

性能上与降级版（每帧 1 个 `drawRect`）是同一量级，实测不出差异——
这个界面每帧真正花钱的是多行 `blur`（`RenderEffect`），
而**当前行的 blur 半径恒为 0**，本就是最便宜的一行。

**兜底**：`TextLayoutResult` 取不到、或字级数据与文本对不上时，
退化为整行高亮。兜底路径仍然存在，只是从常态变成异常。

**待真机验证**：`getHorizontalPosition` 在「折行 + 中英混排 +
`TextAlign.Center`」组合下的表现未经实测。居中对齐下每一折行的
起点 x 不同，需真机确认。

## 五、时钟：绘制阶段自驱动，不提高 tick

`LYRIC_TICK_MS` 保持 **100ms 不变**，`derivedStateOf` 的记忆化不动。

**不把 tick 提到 16ms**：那会让 `LyricsOverlay` 每帧重组，`indexAt` 二分、
`rows` 的 remember 校验、整个窗口的重组判断全跟着跑。这块区域同时是
触摸板，会与手势识别抢同一帧预算——CLAUDE.md 已明确警告过这条。

做法：当前行内部起一个 `withFrameNanos` 循环，把进度写进
`mutableFloatStateOf`，**只在 `drawWithContent` 里读**。
Compose 据此把它降级成「只重绘」，不触发重组或重测量——
与项目里 `graphicsLayer` 位移「走绘制阶段」的口径一致。

起点用一次 `track.currentPositionMs(nowMs)` 对齐，之后靠帧时间自增。
**每行只采样一次，不是每帧一次。**

该时钟本身已是 `positionMs + elapsed × playbackSpeed` 的外推值
（`TrackInfo.currentPositionMs`），在播放器两次回推之间连续且单调，
正适合做扫光的时基，不需要额外的补偿层。

`isPlaying == false` 时挂起循环，扫光停在原地。

## 六、参数化与实验室

`LyricsAnimSpec` 加三个字段：

- 已唱档 alpha
- 未唱档 alpha（当前行内部的对比度）
- 边界软硬度（渐变跨度，0 = 硬边界）

在 `LyricsLabScreen` 加对应滑块，假歌词样本补一条带字级时间表的
（且要有一条长到必然折行的，理由同上）。

**只存内存、不落盘**，复用现有 `LyricsAnimOverride` 与 LAB 角标——
理由同现有三个实验室：歌词观感的好坏没有「因人而异」的成分，
做成可持久化配置只会让线上出现没人能复现的观感问题。

**不加用户开关**：有 `yrc` 就扫光、没有就自动退化，静默降级。
口径同译文（「没有译文是常态而非异常」）。译文那个开关有理由
（中文歌不需要译文，且译文占行高），而「用户为什么想关掉逐字」
想不出理由——有数据就是更准的信息。

## 七、测试

纯逻辑部分全部 JVM 单测：

- **`YrcParserTest`**：格式解析、元信息行（`[0,0]`）丢弃、字级起点单调、
  末字终点等于行终点、畸形输入回落 null 而非抛异常
- **择一逻辑**：有 `yrc` 用 `yrc`、无则回落 `lrc`，
  **专门拦住「跨时间轴混用」**——这是本次最容易写错的地方，
  且错了在界面上表现为「扫光跑在字前面」，不会被认成数据缺陷
- **进度换算纯函数**（行时间表 + 当前 ms → 0..1）：行首前为 0、
  行尾后为 1、字与字的间隙内单调不回退

渲染与时序照例靠实验室 + 真机验证。真机回归项：

- 有 `yrc` 的歌（如 1901371647 孤勇者、1859245776 Stay）扫光跟得上演唱
- 无 `yrc` 的歌（如 28643004）退化为整行高亮且**与改动前无差别**
- **折行的长句**扫光在第一折行走完后才进入第二折行，
  不是两行同时被切一半
- 暂停时扫光停住，恢复后从原位继续
- 切歌时扫光立刻对齐新歌，不残留上一首的进度
- 非网易云播放器（mediaId 非纯数字）不受影响，仍走现有的挡掉路径
