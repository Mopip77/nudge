# nudge —— 实时歌词展示 设计文档

日期：2026-09-20
状态：已验证核心技术假设，待实现

## 1. 目标

在主界面展示与播放进度同步的滚动歌词，作为触摸板下方**若隐若现的背景层**。

核心约束来自 nudge 的定位：这是个盲操 app，触摸板的手势识别可靠性高于一切。**歌词是锦上添花，绝不能干扰手势。**

**首版范围**：逐行歌词，居中对齐，当前行高亮。不做逐字（yrc）、不做缓存、不可交互。

## 2. 关键技术验证结论

以下结论均在真机（三星 SM-G9810 / 网易云 9.5.95）实测得出，非推测。

### 2.1 歌曲 ID 可直接获取，无需搜索匹配

这是整个设计成立的基石。

`MediaMetadata.METADATA_KEY_MEDIA_ID` 就是网易云的**真实歌曲 ID**，可直接用于查询歌词接口。真机 dump 与接口返回逐项对照：

| | MediaMetadata（设备读取） | `song/detail` 接口返回 |
|---|---|---|
| MEDIA_ID | 1995629530 | （查询键） |
| 歌名 | romance | romance |
| 歌手 | KidSnorlax | KidSnorlax |
| 时长 | 135400 ms | 135400 ms |

时长**逐毫秒一致**，证明拿到的就是同一首歌。

**由此导出的最重要结论**：歌词与音频**同源**，时间轴天然对齐。不存在"匹配错歌导致时间轴偏移"的问题，因而**不需要**按歌名搜索、不需要模糊匹配、不需要时长校验兜底。这些都是第三方歌词库（lrclib 等）方案才需要的补丁。

`TrackInfo.mediaId` 字段现有代码**已在读取**，无需改动数据层。

### 2.2 歌词接口

```
GET https://music.163.com/api/song/lyric?id=<MEDIA_ID>&lv=1&kv=1&tv=-1
Header: User-Agent: Mozilla/5.0
        Referer:    https://music.163.com
```

实测**无需登录、无需 Cookie**，真机上直接 curl 可通。返回 JSON：

| 字段 | 内容 | 首版是否使用 |
|---|---|---|
| `lrc.lyric` | 标准 LRC，`[mm:ss.SSS]文本` | ✅ 唯一数据源 |
| `tlyric.lyric` | 中文翻译（外语歌常有） | ❌ 暂不使用 |
| `yrc.lyric` | 逐字歌词，`[行起,行长](字起,字长,0)字` | ❌ 暂不使用 |
| `code` | 200 为成功 | ✅ 用于判成功 |

注意 `yrc` **并非每首歌都有**（《发如雪》有，romance 没有）。这是首版不做逐字的原因之一：必须带降级路径，复杂度翻倍而盲操收益有限。

### 2.3 已排除的方案

均经实测，非推测：

| 方案 | 排除原因 |
|---|---|
| 通知栏歌词 | 网易云 9.5.95 通知 extras 中**无歌词字段**，仅有歌名/歌手；`lyric` 只是个打开桌面歌词的 PendingIntent 按钮 |
| 本地歌词缓存文件 | 新版存于应用私有目录，非 root 不可读 |
| SuperLyric / Xposed Hook | 需 root，主力机无 root |
| lrclib 等第三方 LRC 库 | 音频版本不一致导致时间轴整体偏移；且冷门中文歌覆盖差 |

## 3. 架构

歌词功能作为独立一层接入，不改动现有手势链路：

```
        ┌──────────── TrackpadScreen ────────────┐
        │  TopBar（歌名/歌手/进度，不变）          │
        │  ┌──────────────────────────────────┐  │
        │  │ Box（原触摸板区域）                │  │
        │  │   ├─ 底层：LyricsOverlay ← 新增   │  │
        │  │   └─ 上层：触摸层（不变）          │  │
        │  └──────────────────────────────────┘  │
        └────────────────────────────────────────┘
                          ▲
                    LyricsState
                          │
        LyricsRepository ─┴─ LyricsFetcher（HTTP）
                │
           LrcParser（纯 Kotlin，可单测）
```

新增文件：

| 文件 | 职责 | 可单测 |
|---|---|---|
| `lyrics/LrcParser.kt` | LRC 文本 → `List<LyricLine>`；纯函数，不依赖 Android | ✅ |
| `lyrics/LyricLine.kt` | 数据类 `(timeMs, text)`；含"按位置找当前行"逻辑 | ✅ |
| `lyrics/LyricsFetcher.kt` | HTTP 请求 + JSON 取 `lrc.lyric`，用 `HttpURLConnection` | ❌ 需网络 |
| `lyrics/LyricsRepository.kt` | 按 mediaId 拉取，暴露状态；管理请求生命周期 | ❌ |
| `ui/LyricsOverlay.kt` | Compose 渲染层 | ❌ |

`LrcParser` 刻意做成**纯 Kotlin 无 Android 依赖**，与 `GestureRecognizer` 同样的理由：解析边界条件多（毫秒位数不一、一行多时间戳、元信息行、空行），靠真机手测不现实。

## 4. 数据流

```
mediaId 变化 ──► LyricsRepository.load(mediaId)
                      │
                      ├─ mediaId 为空/非数字 ──► Unavailable（不请求）
                      │
                      └─ IO 线程 HTTP ──► 成功 ──► LrcParser ──► Loaded(lines)
                                          失败 ──► Unavailable

渲染：position（由 TrackInfo.currentPositionMs 推算）+ lines ──► 当前行索引 ──► 滚动 + 高亮
```

状态模型：

```kotlin
sealed interface LyricsState {
    data object Idle : LyricsState                       // 无歌曲
    data object Loading : LyricsState                    // 请求中
    data class Loaded(val lines: List<LyricLine>) : LyricsState
    data object Unavailable : LyricsState                // 纯音乐/网络失败/无歌词
}
```

`Loading` 与 `Unavailable` 在 UI 上**表现一致：什么都不显示**。区分它们只为便于调试与后续演进——盲操 app 不该为"正在加载"这种事打扰用户。

## 5. 关键设计决策

### 5.1 歌词层绝不参与触摸（最重要）

歌词是**纯展示**，不可滑动、不可点击跳转。

实现上，`LyricsOverlay` 画在触摸 `Box` 的**内部底层**，触摸层保持在其上方。现有 `pointerInteropFilter` 的代码**一行都不用改**，歌词层也不添加任何 pointer 修饰符，因此不可能拦截或延迟手势事件。

这不只是"首版砍功能"——盲操场景下，可交互的歌词反而会与手势语义冲突（一次滑动到底是"跳转歌词"还是"手势"？）。保持只读是长期设计，不是权宜。

### 5.2 重组隔离：高频刷新不得拖慢触摸

滚动要平滑，歌词的重组频率必须高于现有进度条的 500ms（拟 100ms）。而这块区域同时是触摸板，**这是本功能唯一的真实性能风险**。

应对：

1. **状态下推**。驱动滚动的 `position` tick 状态**只存在于 `LyricsOverlay` 内部**，不提升到 `TrackpadScreen`。Compose 只重组读取了变化状态的作用域，因此 tick 变化不会触发触摸层重组。
2. **当前行索引记忆化**。用 `derivedStateOf` 让高亮/滚动只在**行号真正变化**时才触发重组，而非每个 tick。一行歌词通常持续数秒，实际重组频率远低于 100ms。
3. **动画用 `Animatable`**，其逐帧更新走的是 Compose 的 draw 阶段，不触发重组。

**验收要求**：真机上开启歌词后复测五种手势，识别成功率与无歌词时无差异。若实测有影响，退而降低 tick 频率（200ms）——滚动平滑度让位于手势可靠性。

### 5.3 视觉：当前行清晰，其余压淡

作为背景层，需在"能读"与"不喧宾夺主"之间取平衡：

| | 当前行 | 相邻行 | 更远的行 |
|---|---|---|---|
| 透明度 | 0.85 | 0.35 | 0.18 |
| 字号 | 17sp | 15sp | 15sp |
| 字重 | Medium | Normal | Normal |

全部**居中对齐**。当前行固定在容器**垂直中央**，歌词整体上下滚动。

切换效果参考 Apple Music：换行时**平滑过渡**而非瞬切——透明度与位置同时做动画（`tween`，约 350ms，缓动 `FastOutSlowInEasing`）。这个时长是"跟得上换行"与"看得出动效"的折中，需真机微调。

### 5.4 不做缓存

每次切歌直接请求。理由（用户明确）：很少重复听同一首歌，缓存收益低，不值得引入存储与失效逻辑。

单曲循环/切回上一首会重复请求，可接受：一次请求仅几 KB。

### 5.5 网络的代价

必须为 app 新增 `INTERNET` 权限，这与项目原有"零网络、仅一个通知权限"的气质有冲突。这是拿到同源歌词的**唯一途径**（见 §2.3 排除表），是明确的取舍而非疏忽。

实现上的克制：

- 用 JDK 自带 `HttpURLConnection`，**不引入任何 HTTP 库**（OkHttp/Retrofit），保持依赖表干净
- 用 `org.json`（Android 内置），不引入 JSON 库
- 仅在 mediaId 变化时请求一次，不轮询
- 超时 5 秒，失败即静默降级为无歌词，**绝不弹错误提示**打扰盲操

接口为网易云非公开接口，存在改版失效风险。失效表现为"歌词不显示"，不影响任何现有功能——这是可接受的失败模式。

## 6. 错误处理

全部失败路径**统一静默降级为"不显示歌词"**，绝不打断使用：

| 情况 | 处理 |
|---|---|
| 无网络 / 请求超时 | `Unavailable`，不重试 |
| mediaId 为空或非数字（非网易云播放器） | 不发起请求 |
| `code != 200` / 无 `lrc` 字段 | `Unavailable` |
| 纯音乐（歌词为空或仅元信息行） | `Unavailable` |
| 解析异常 | 捕获，`Unavailable` |
| 切歌时旧请求未完成 | 取消旧请求（协程随 key 变化自动取消），避免旧歌词错配到新歌 |

最后一条尤其重要：快速连续切歌时，若不取消旧请求，可能出现"显示上一首歌词"的错配。

## 7. 测试

### 单元测试（JVM，随 `./gradlew test`）

`LrcParser` 是测试重点，覆盖真实 LRC 的边界情况：

- 标准 `[mm:ss.SSS]` 与两位毫秒 `[mm:ss.SS]` 均能解析
- 元信息行（`[by:xxx]`、`作词 :`）不崩溃
- 一行多时间戳（`[00:10.00][01:20.00]同一句`）展开为多行
- 空歌词行保留时间戳（用于留白停顿）
- 结果按时间**升序排序**
- 纯音乐 / 空文本 → 空列表
- 畸形输入（缺右括号、非数字）不抛异常

`LyricLine.indexAt(positionMs)` 的边界：

- 位置早于首行 → -1（不高亮任何行）
- 恰好等于某行时间戳 → 命中该行
- 位置晚于末行 → 命中末行
- 空列表 → -1

### 真机验证（无法自动化）

1. **手势回归**（最关键）：开启歌词后复测五种手势，识别率与之前无差异
2. 歌词与演唱同步，无明显偏移
3. 切歌时歌词正确更新，快速连切无错配
4. 纯音乐 / 飞行模式下静默无歌词，app 正常可用
5. 暂停时歌词停止滚动，恢复后位置正确

## 8. 不做的事（首版）

| 项 | 原因 |
|---|---|
| 逐字（yrc）高亮 | 并非每首歌都有，需降级路径；盲操下逐行已够 |
| 翻译对照（tlyric） | 双行会让背景层过于嘈杂 |
| 歌词缓存 | 用户明确不需要 |
| 点击/滑动歌词跳转 | 与手势语义冲突，见 §5.1 |
| 非网易云播放器的歌词 | 其 mediaId 非网易云 ID，无从查询 |
| 设置项开关 | 先默认开启，真机验证后再决定是否需要 |
